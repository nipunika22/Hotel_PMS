# Dining Module Final Regression Report

**Audit date** · 26 November 2026  
**Release readiness** · **HOLD**

The integrated discovery, reservation, arrival, order, bill and cash-to-sales workflow passed in Chrome. Isolated API tests also passed for external card recording, signed PayHere outcomes and eligible hotel folio postings. Three defects block release. A legacy route charged a checked-out stay with a paid invoice. Another legacy route reopened a guest-cancelled reservation. Concurrent public bookings assigned the same table to two confirmed parties at the same time. Two additional catalogue defects are listed below.

## Scope and execution

The audit used the workflow analysis for the original reservation and catalogue paths, the operations QA report for order and settlement coverage, and the payment security report for regression targets. [Workflow analysis](DINING_MODULE_WORKFLOW_ANALYSIS.md) · [Operations QA](RESTAURANT_OPERATIONS_QA_REPORT.md) · [Payment security fixes](PAYMENT_SECURITY_FIX_REPORT.md)

- Backend tests ran from a temporary source copy with project dotenv files excluded. Tests that needed a configured database used separate fixture databases on a disposable loopback MongoDB replica set. Suites with their own fixtures kept them. Tests hard-coded to port 5000 were directed to a temporary loopback listener where applicable. Four suites were rerun to correct a missing sibling frontend path or to allow the runner to exit after assertions.
- The production-mode frontend build used `/api` against the temporary local backend for Chrome. Browser traffic to other HTTP origins was blocked. PayHere outcomes came from locally signed fixture callbacks. No gateway, production data or deployed application was accessed. The audit added only this report to the project.

## Remaining bugs and recommendations

| Priority | Finding and evidence | Recommendation |
|---|---|---|
| High · release blocker | **Legacy folio posts after checkout.** The observed LKR 225 expense landed outside the already-paid invoice. The legacy handler checks for a same-property stay and conflicting booking payments, then writes the expense without checking active check-in or an existing invoice. [Legacy folio controller](backend/controllers/restaurantController.js#L1418) | Share stay eligibility and write serialization across both dining charge paths. Test checked-out and already-invoiced stays, plus a checkout/posting race. |
| High · release blocker | **Legacy staff status update reopens cancelled reservations.** A permitted staff user could change a guest-cancelled reservation back to `CONFIRMED` and then mark arrival. [Legacy status route](backend/routes/restaurantRoutes.js#L228) · [Status handler](backend/controllers/restaurantController.js#L1361) | Enforce permitted state transitions across staff updates. Add a regression for guest cancellation followed by staff confirmation and arrival. |
| High · release blocker | **Concurrent public bookings can double-assign a table.** In one four-request run, all four returned `201` and MongoDB held two `CONFIRMED` rows for the only table at the same date and time. In another run, one of four received the table and three were confirmed unassigned. The observed assignment count depended on timing. [Table selection](backend/controllers/restaurantController.js#L527) · [Reservation insert](backend/controllers/restaurantController.js#L649) | Make overlapping slot allocation atomic. Define whether unassigned reservations should be accepted and how they appear to guests and staff. Add parallel creation coverage that checks the persisted assignments. |
| Medium · security | **Inactive restaurant menu stays publicly accessible.** The inactive fixture’s direct menu route returned `200` and an item. Buffet and offer routes also returned `200`. The venue was absent from discovery, detail returned `404`, and booking returned `400`. This exposed same-property unpublished menu data in the tested case. [Menu](backend/controllers/restaurantController.js#L215) · [Buffets](backend/controllers/restaurantController.js#L265) · [Offers](backend/controllers/restaurantController.js#L300) | Apply consistent active-venue checks to the public catalogue routes. Add direct URL tests for deactivated venues. |
| Medium | **Restaurant tagline update silently drops the field.** Admin update returned `200` with an empty `tagline` after sending `Sunset sips and wood-fired skewers`. The field is absent from the update allowlist and is displayed by the storefront. [Failing assertion](backend/tests/restaurant.test.js#L521) · [Update handler](backend/controllers/restaurantController.js#L907) · [Storefront](frontend/src/pages/DiningLanding.js#L361) | Support validated updates for the field or explicitly reject it if it should be read-only. Verify the update through a subsequent public read. |

Re-run the historical-price folio assertion with both a priced eligible booking and a historical booking missing its amount. Make staff messaging and the test contract explicit for the historical case. Keep the stricter folio guards and the duplicate-settlement and cancellation callback cases in the release gate. [Legacy folio test](backend/tests/restaurant.test.js#L569) · [Historical price guard](backend/controllers/restaurantController.js#L1430)

## Unverified behavior

- Hosted checkout, browser return from PayHere, callbacks transported by the provider, provider-side duplicate collection controls, real refunds and external terminal capture were outside this audit. The late-success probe establishes how the application accounts for a contradictory callback locally.
- Physical printing, other browsers and viewport sizes, the full role and navigation matrix, multi-instance concurrency, rate limiting under load, and production database indexes and historical records remain unverified. The browser run used a fixture guest and admin. Department and staff grants were also exercised at the API level.
- Kitchen ticket routing, walk-in operations and settlement refund workflows had no end-to-end coverage in this audit. Existing automated tests exercised the general refund endpoint locally. Dining-specific refund behavior was outside the integrated run.
